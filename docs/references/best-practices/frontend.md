# Best Practices — 前端（React / antd / ECharts）

> 2026-09-23 从 [`../best-practices.md`](../best-practices.md) 拆分（内容原样搬移，未改写）。
> 检索方式（探测器映射表）与**写入门槛**见 [`../best-practices.md`](../best-practices.md)。

- 多级联动多选控件应以上层选项动态约束下层候选集，并在上层变更时剔除失效下层值，保证提交数据始终满足父子层级关系；联动筛选状态应直接由当前上层已选值派生（而非间接缓存变量），确保禁用态、placeholder 与候选集在同一次渲染中保持一致。
- 当分类数据同时存在"官方成员映射"和"用户自定义标签"时，应在树统计、详情列表和兜底分类中统一按并集去重计算，防止展示与筛选结果不一致；行业树统计应与可展示股票集合保持同一口径（以 `stocks` 为准），为无法映射到有效层级的标的提供"其他"兜底分类，避免前端总量与分组总和不一致。
- 对会影响聚合视图的数据编辑操作，应成对执行"前端 query invalidation + 后端 Redis 聚合键清理"，避免页面在 TTL 期间显示过期计数。
- 公共类型/映射函数应集中在语义匹配的模块中（如 `BackendStockEnriched` 从 `swIndustry.ts` 移到 `stocks.ts`），避免使用者因模块名误导而重复实现；单股详情页 FundamentalCards 估值指标依赖 enriched 接口，新增详情接口时应复用同一 SQL 查询并统一缓存 key 前缀（如 `stock:enriched:`）以保证数据一致性。
- 封装组件的 prop 语义即契约（如 EChart 的 silent 必须真正关 animation+tooltip，不能用换 renderer 这类无副作用的近似实现），文案/标签类展示值应由后端 payload 下发而非前端维护重复映射表（只留纯展示常量如颜色）——否则后端语义演进时前端会静默回退或误标；前后端透传的 JSONB dict 键名要保持 snake_case 一致（前端读 camelCase 会静默不渲染，类型断言不报错）。
- 行业分级页面建议采用"层级选择状态 + 统一个股表格"的单一数据视图模式，避免一级/二级/三级分别维护重复表格逻辑导致状态不一致；涉及层级导航的页面用显式独立路由承载每一级职责，让"点击下钻"和"同页筛选"交互分离，同一层级列表内的点击交互统一为路由下钻并保持视觉反馈一致。
- 板块中心类页面推荐采用"主界面分组预览 + 详情页完整表格"的双层结构，既保证信息密度也降低首次加载认知成本。
- 前后端联调阶段应优先让页面消费真实后端字段并通过前端适配层兜底缺失指标，避免长期依赖 mock 造成接口契约漂移；迁移前端到真实后端接口时，先建立统一的 API 适配层集中做字段映射，再逐页面替换调用以减少回归风险；分层行业页面去 mock 时应先后端化层级树和分层股票查询，再让前端页面复用同一套树数据以保证路由与数据口径一致。
- Ant Design Table 的分页大小切换应由组件状态显式持久化（避免把 `pageSize` 写成固定常量），否则在排序/筛选触发重渲染后退回初始值；当页面展示服务端分页切片时，分页总数与最大页必须用后端 `total` 而非当前页 `data.length`，并由父组件统一驱动 `current/pageSize` 避免 UI 与请求状态漂移。
- ROE、营收同比、净利润同比等财务成长指标需 TuShare `fina_indicator`/`profit_data` 接口支持、后端入库后方可展示；在此之前 FundamentalCards 应提供降级展示策略或临时隐藏相关指标。
- echarts-for-react 默认 merge 模式下，用户交互过的组件状态（如 dataZoom 滚轮缩放窗口）不会被新 option 同名配置重置：数据全集切换的图表必须 `notMerge`（对齐 shared/ui/EChart 封装），且不要用固定 start/end 百分比裁剪初始视图——周期切换类交互的正确语义是"所选区间全量展示 + 每次切换重置缩放"。
- antd 栅格内卡片等高要"双保险"：内容侧 Typography `ellipsis`（描述 `tooltip:true`）消除换行撑高，布局侧 Col `display:flex` + Card `height:100%` 拉伸兜底；flex 行内文本省略号必须给文本容器 `minWidth:0`（flex item 默认 min-width:auto 不收缩），Tag/图标侧补 `flexShrink:0`。
- 重复图表组件的合并应先落纯函数层（计算/格式化/裁剪）并配 barrel 导出，且把类型签名当依赖契约先于组件实现冻结（任务 brief 的 Interfaces 块即签名源）——后续 UI 任务只依赖稳定签名，不再各自重复实现；brief 代码块可用 diff 逐字校验落地无漂移。
- 微服务架构中的身份认证应采用“Gateway 同源 BFF + HttpOnly Session Cookie + 短时非对称签名断言（Principal Assertion JWT）+ 下游本地 JWKS 验签”的零信任模式，彻底消除 XSS 窃取与未签名 Header 伪造越权风险。
- 重复图表组件的合并应先落纯函数层（计算/格式化/裁剪）并配 barrel 导出，且把类型签名当依赖契约先于组件实现冻结（任务 brief 的 Interfaces 块即签名源）——后续 UI 任务只依赖稳定签名；brief 代码块可用 diff 逐字校验落地无漂移。
- ECharts option builder 保持返回未注解的结构化对象（推断类型天然可赋给 `Record<string, unknown>`），formatter 一律收 `params: unknown` 再局部断言；当 `string` 参数要索引 `Partial<Record<字面量联合,…>>` 时直接把参数收窄为字面量联合类型（如 `MaKey`），比在索引处加 `as` 断言更不易漂移。
- antd 5.x 命名导出随小版本漂移：子组件（如 CheckableTag）可能只挂在主组件命名空间（`Tag.CheckableTag`）而非顶层导出，逐字移植参考代码时先对齐代码库内同组件既有用法再定 import 形态；此类 TS2305 还会连带制造"参数隐式 any"的次生报错，修掉根因即一并消除。
- 后端能力未就绪（如复权因子懒加载中）的前端控件应降级为"禁用+Tooltip 提示"而非条件隐藏：DOM 结构保持稳定让 E2E 能以长超时轮询等就绪，且禁用只锁视觉层——受控 state 与 queryKey 不变、value 固定为当前真实展示值，能力恢复后无缝启用且不发额外请求。
- 多源单位在映射层一次性归一（元），消费端只做展示分档：后端字段单位（TuShare total_mv 万元/amount 千元）与前端 formatCap 分档基准（元）错位时，在唯一 mapper 处换算并注释口径，表格列新增时核对 unit props——多消费点各自补偿是单位错误的标准成因。
- **容器 `Up` 不等于服务可用；镜像自带的 entrypoint 脚本是启动路径上的隐形依赖**：本仓 frontend 换成官方 `nginx:alpine` 后，其 `/docker-entrypoint.d/10-listen-on-ipv6-by-default.sh` 在容器内**卡死不退**，`nginx` 从未启动，而 `docker ps` 显示 Up、只有 Traefik 在 502。两条做法：① 对静态配置的服务，直接 `ENTRYPOINT []` + 自己的 CMD，别让基础镜像的初始化脚本参与启动（它们的假设往往建立在默认配置上，而我们覆盖了默认配置）；② 每个对外服务配 healthcheck（`wget -qO- http://127.0.0.1/`），把"Up 但不可用"变成 `unhealthy`。排查口诀：先看**容器内**是否真的在 listen（`netstat`/`wget 127.0.0.1`），再看进程树里是不是有卡住的初始化脚本（`docker top`）——不要只看容器状态与镜像标签。
- **硬编码平台/架构的构建步骤，会在"基础镜像换成真多架构"那一刻集中爆掉**：本仓 frontend 曾写死 `npm i @rollup/rollup-linux-x64-gnu`，在第三方**单架构（amd64）**基础镜像下 arm64 腿也照装不误（那腿其实是 amd64 userland + QEMU），于是"CI 双平台通过"给了多架构可用的错觉；换成官方多架构 `node:22` 后 arm64 腿变成真实 arm64，立刻 `EBADPLATFORM` 失败。两条做法：① 构建步骤里一律按 `uname -m` 或 `dpkg --print-architecture` 选平台包，不写死；② 判断"多架构是否真的成立"要看**基础镜像的 manifest 列表**（`docker buildx imagetools inspect <base>` 是否同时列出 amd64/arm64），而不是看自己的产物 manifest —— 后者只是被 buildx 标上的名字。
- **测试夹具必须能走到出错的代码分支，否则"全绿"是假的**：本次修盘中崩溃时，第一版 e2e 夹具是「5板/2家 vs 2板/3家」，注入原始缺陷（`null.localeCompare`）后测试**依然通过** —— 因为排序比较器是 `streak → count → 名称` 的短路写法，两条数据在数值上就分出胜负，读取 null 的最后一个子句根本没执行。改成两条 `(max_streak, zt_count)` 完全并列后，注入缺陷立刻变红。通用做法：凡是"某个字段只在特定分支被读取"的缺陷，夹具必须**主动制造走到该分支的条件**（并列/边界/同值），并用**注入缺陷反证**一次（把缺陷临时加回去，确认测试真的会红）——"修复版绿"从不等于"测试有效"。
- **类型撒谎就是运行期崩溃的许可证**：`SectorLimitUpItem.l3Code: string` 而接口实际返回 `null`，`tsc` 于是放过 `a.l3Code.localeCompare(...)`，上线后一个 null 就炸掉整页。修法不是加 `?.`，而是**先把类型改成说实话**（`string | null`），此后所有未做空合并的写法都会在编译期报错 —— 把"靠人记住"变成"编译不过"。同理，接口新增可用字段（本例 `board_name`）必须同时改 Pydantic schema，否则后端算好了、序列化时被悄悄丢掉。
- **基础镜像用浮动 tag，等于把"上游补丁版本"变成"自己发版时的下载量"**：实测本仓 v0.0.5 在服务器上拉了 14 分钟 —— 上游 `python:3.13-alpine` 一动，`uv pip install` 产出的依赖层 digest 全变，服务器只能重下整套 site-packages（~300MB，链路 ~600KB/s）。改成 `FROM image:tag@sha256:<manifest digest>` 后，只要 lock 不变依赖层就稳定，发版只下几 MB；代价是要定期（季度/跟安全更新）手工更新 digest —— 把"取新 digest 的命令"写进 Dockerfile 注释与部署文档，别留给记忆。
- **"多平台构建成功"不等于"多平台产物可用"**：本仓基础镜像来自华为 SWR 的 `ddn-k8s` 源，实测 `python:3.13-alpine`/`node:22`/`nginx:alpine` **只有 amd64**，buildx 对 `--platform linux/arm64` 只给一条 `InvalidBaseImagePlatform` **警告**、然后照旧用 amd64 基础层 + QEMU 构建，产物 manifest 里却标着 `arm64` —— 真机上是 `exec format error`。判定方法：`docker image inspect <产物> --format "{{.Architecture}}"` 看的是**标称**架构，要确认基础层真实性得看 buildx 警告或 `docker buildx imagetools inspect <base>` 的 manifest 列表；只要目标机不是本机架构，就该先验一次"能起来"再谈多平台。
- **bind mount 单文件 + 原子替换（tar/scp 覆盖、编辑器 safe-write）＝ 容器里还是旧内容**：宿主侧 `mv`/`tar xzf` 会换掉 inode，而单文件 bind mount 绑的是 inode，于是"改了配置、reload 也说 unchanged、`restart` 也无效"——实测 Caddy 的 HSTS 就这么消失了一轮（容器内 `grep` 计数 0、宿主侧 1）。两条做法：① 要频繁更新的配置**挂目录**而不是挂单文件（本仓把 `gateway/Caddyfile` 移成 `gateway/caddy/Caddyfile` 并挂 `./gateway/caddy:/etc/caddy:ro`）；② 排查时先比对**容器内**与宿主侧的同一文件（`docker exec <c> grep -c <关键字> /path`），别只 `docker exec cat` 一次就下结论；③ 单文件挂载来不及改时，`up -d --force-recreate <svc>` 可强制重新挂载（比 `restart` 有效，因为 restart 不重建挂载点）。
- **HSTS 必须由终结 TLS 的那一层下发**：上游网关看到的是明文 HTTP，其 `stsSeconds` 不生效（实测无 header）；而用 `forceSTSHeader: true` 强发又会在本地 `http://localhost` 上发 HSTS，把开发机浏览器钉到 HTTPS（自伤）。本栈因此把 HSTS 写在 Caddy 站点块里，本地开发与生产自然隔离。
- **给已有应用网关加 TLS，用"边缘终结 + 原网关不动"的两跳，别叠第三个代理**：本栈路由/鉴权（forward-auth 注入断言）、限流、安全头全在 Traefik 的 labels 与动态配置里，TLS 交给前面的 Caddy 终结即可（Caddy 自动签发续期，不需要 certbot）；再插一层 Nginx 只会多一个"把 `X-Forwarded-*` 传歪"的机会，而 Nginx 的静态服务角色早已由 frontend 容器占据。三个必须一起改的位置：① Caddyfile 的 `reverse_proxy <网关服务>:80`；② **网关必须显式信任上游网段**（Traefik 的 `forwardedHeaders.trustedIPs`，默认不信任任何 XFF）—— 否则审计日志与限流记的是边缘容器的内网 IP、协议退化成 http；③ 用 `ports: !override []` 把宿主机 80/443 从原网关**整体转交**给边缘容器（Compose ≥2.24；追加式合并会让两个容器抢同一端口而 `up` 失败），并把它放进仅生产使用的 override 文件，本地开发流程零影响。另外：ACME 状态（证书+账号）必须落在持久卷里，删卷会重复签发并撞 Let's Encrypt 的每周上限。
- **迁移数据时"先恢复、再起应用"不是洁癖，是省钱**：本栈 API 启动钩子 `data_init.maybe_seed_on_startup()` 无条件执行，遇到空 `stocks` 表就会后台回补全量 3 年行情（烧 TuShare 额度）。实测先 `pg_restore`（501MB / 2m33s）再起应用，覆盖度检查只补了 19 只新股、12,446 行、15 秒完成；反过来先起应用就是几百万行回填。配套检查：恢复后立刻对账行数与 `alembic_version`（本例逐项与源库一致 → `migrate` 服务自动 no-op，不需要也不该手工 `alembic stamp`）。
- **服务器访问 GitHub 受限时，用 codeload tarball 代替 git clone**：实测 `git clone`（HTTPS 与 HTTP/1.1）都失败（`HTTP/2 stream not closed cleanly` / `GnuTLS recv error -110`），而 `curl -sL https://codeload.github.com/<owner>/<repo>/tar.gz/refs/tags/<tag> | tar xz --strip-components=1` 稳定 1MB/s。副产品是好事：**tarball 天然只含入库文件**，不会把本机 `.env`、未入库的 `docker-compose.override.yml`（卷名 pin）带上服务器——这正是「环境假设泄漏」最常见的两个来源；代价是服务器上没有 git 历史，后续升级靠"重新拉新 tag 的 tarball 就地覆盖"（`.env` 不在 tarball 里，不会被覆盖）。
- **运维端口的默认绑定要 fail-safe：只绑回环，判断标准是"公网能不能连"而不是"我本地要不要用"**——本仓 `postgres`/`redis` 曾绑 `0.0.0.0:5433/6380`，口令还是默认值（Redis 甚至无认证），于是网关侧辛苦搭的 forward-auth 完全可被绕过：直连数据库端口即可。改成 `127.0.0.1:5433:5432` 后，宿主机上的本地开发与 `pytest`（连 `localhost:5433`）零影响，而外部网络访问不到；对外暴露面收敛成"只有 gateway 的 80/443"这一条可审计的规则。核验动作固定两条：`docker compose ps` 里**只有**网关出现 `0.0.0.0:` 映射；从另一台机器（或本机 LAN IP）连该端口应被拒。遗留的第二份 compose（本例 `backend/docker-compose.yml`）也要一起改——它最容易漂移成"绕过收敛的后门"。
- **Docker 镜像瘦身要先量再改，且十有八九输在"stage 之间整目录拷贝"**：本仓 backend 从 513MB 降到 351MB，最大一笔不是删依赖，而是 runtime 不再 `COPY --from=builder /usr/local/bin /usr/local/bin`（那把 `uv`/`uvx`/pip 及 builder 的整套 python 工具链一起搬进产物）——改成只白名单拷 `uvicorn`+`alembic` 两个真正被调用的 console script（worker/scheduler 走 `python -m`，不需要任何脚本）。顺序：`docker run --rm --entrypoint sh <img> -c "du -sh /usr/local/bin /usr/local/lib/python3.*/site-packages /app"` 定位大头 → 再决定删什么；同时**别删传递依赖**（本例 `py_mini_racer`/`pandas`/`numpy` 是 akshare 的运行时依赖，共 ~185MB 但删了就断功能），预编译字节码则是"启动略快、体积略大"的取舍，服务器部署看 pull 体积时应当不做。
- **自证命令要区分"宿主侧键名"与"容器内键名"**：compose 的 `${AUTH_COOKIE_SECURE}` 进容器后叫 `COOKIE_SECURE`（`AUTH_JWT_PRIVATE_KEY_PEM`→`JWT_PRIVATE_KEY_PEM`、`AUTH_TRUST_FORWARDED_FOR`→`TRUST_FORWARDED_FOR`），拿宿主侧名字去 `docker exec ... $VAR` 只会得到空串，于是把"其实已生效"的配置误判为"没配"并写进文档（本轮就这么错记了一条，靠复查才订正）。凡是写给运维的自证脚本，必须在**目标容器里**用**真实键名**跑一次并把期望值写出来，而不是凭 compose 里的名字推断。
- **示例配置文件"存在"不等于"落位正确"：要验证「按文档照做后，关键变量到底有没有值」**——本仓库同时有 `.env.docker.example` 与 `backend/.env.example`，文档却教把前者复制成 `backend/.env`，而 compose 的 `${VAR}` 插值**只读项目根目录 `.env`**，于是鉴权类密钥（JWT 私钥、`INTERNAL_API_TOKEN`、Secure-Cookie/XFF 开关、`APP_ENV`）全部静默回落到开发默认值：生产上表现为「跳过生产强校验 + 私钥每次重启轮换 + 内部调用不带 token」，而且**一个错误都不报**。两条可复用做法：① 部署文档必须写清「**谁读这个文件**」（compose 插值 vs 容器 `env_file`），一种角色一个文件，并给出"复制到哪"的绝对路径；② 附一段"启动后自证"命令（`docker compose config | grep 关键键` + 容器内变量自查空/非空），把「密钥为空」从静默降级变成一眼可见。
- **门禁要在自己仓库的 CI 口径下跑，而且要在 commit *之前*跑**：CI 的 lint job 跑的是 `ruff check` **和** `ruff format --check` 两条，`self_review.sh` 里对应逻辑也写了 —— 但只采集**工作区**改动，于是「先 commit 再跑 self_review」会拿到空改动集、整段 lint 跳过并打印绿勾，实测就这么漏了一个 `ruff format` 违规，本地全绿推到 CI 才红（连带 tag 前必须先把 main 修绿）。两条硬化：① `self_review.sh` 的改动集改为**工作区 ∪ `origin/main..HEAD`**，commit 与否都覆盖；② 声称「门禁绿」前先确认跑的是**与 CI 相同的命令集**（`ruff check` 通过 ≠ `ruff format --check` 通过）。
- **「整站数据全空」先查 cookie，别查数据面：本栈的 Traefik `forward-auth` 对「带 `stockbot_session` 但解析不出 assertion」的请求是 **fail-closed 返 503**（不是 401），而过期/伪造的 session cookie 在生产上极常见 —— 于是 `/api/*` 全部 503，每个页面都渲染成「暂无数据」，看起来像后端/数据库炸了。复现对比（真实浏览器匿名 vs 带坏 cookie）：`/api/v1/concepts?limit=1000` → 200/504 板 vs **503**；概念列表页 → 有数据 vs 0 行。排查口诀：① 无 cookie 的 `curl` 通 ≠ 用户浏览器通（用户的区别就是那个 cookie），要**带/不带 cookie 各跑一次**；② 控制台里的 `401 GET /auth/session` 是匿名会话探测，属良性噪声，别当根因；③ 给 fail-closed 的 503 配一句能自解释的 UI 文案（「登录状态已失效，请重新登录或清除 Cookie」），否则用户只会得到「加载失败」而无法自救。
- **把「缺失」引入一张已有表格时，排序比较器必须先于单元格渲染被修好 —— 否则 `?? 0` 会把「不可判」排成「平盘」**：给概念列表接入 `avg_pct: null` 后，降序比较器 `a[x] ?? 0` 让「不可判」的板块排在下跌板块**之前**（单元格已渲染成 `--`，排序里却是 0），而「0 ≠ 不可判」恰是本模块自己的口径；原 e2e 之所以绿，只是因为夹具里所有值都是正数（「恰好排最后」不是代码性质）。两条同源教训：① 可空字段进排序/聚合前先定**缺失的序**（统一 null-last，升序降序都要处理）并用夹具锁定（夹具里必须有一条会暴露差异的负值）；② 页面级「查看全部」类承诺（行数 / `total`）必须有能区分「信封 total」与「本页行数」的断言 —— mock 里两者相等就等于没测。
- 数值型 tooltip 用"灰标签左 + 右对齐 tabular-nums 数值右"的两列式行布局（flex space-between + min-width），OHLC/涨跌随当日涨跌统一着色、量额中性；横排挤合无对齐基准，是主流行情软件与其余 tooltip 的主要视觉分界。
