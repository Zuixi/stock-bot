# 0017 重算历史时不得把已有好值降级为 NULL

```
status:        accepted
date:          2026-10-16
supersedes:    -
superseded-by: -
```

## 背景

[ADR 0016](./0016-derived-metrics-converge.md) 让派生指标每天 3 次重算最近 10 个交易日窗口
（"重算区间"是它的自愈机制）。但共享写路径 `industry_metric_repo.upsert_metrics` 对 `value` /
`extra` 是 `excluded.*` **直接覆盖**（只有 `published_at` / `caliber_version` 用 `coalesce`，
那是 Ruling 36 明确限定的两列）。两者相乘的后果：某一轮 TuShare/AKShare 返回空时，窗口内
**早就正确观测到**的历史值会被改写成 NULL。复核时实测：`above_ma20_ratio` 2026-10-14 的
`23.2655` 被一行 `value=NULL` + `source_empty` 覆盖，旧值无处回退。

## 决策

**在收敛器这一层做降级保护**（不动共享写路径）：重算前对窗口做非 NULL 快照，
重算后凡"快照非 NULL 而现状为 NULL"的行，用同一唯一键 upsert **恢复回旧值**，并**告警**
（`value_downgrade_blocked:<leg>=<n>`）。方向性是关键：

- **值 → NULL 拒绝**（降级，历史被改坏）；
- **NULL → 值 放行**（源侧迟到补数，例如 QVIX 本轮回填）；
- **值 → 值 放行**（修订）。

故它不妨碍自愈，只妨碍"越算越差"。composite 同享该保护（其值由**当时的**齐备成分算出，
分位窗口是回看的 ⇒ 一旦算过即稳定，不该被"今天的缺数"抹掉，headline 也不该来回跳）。

## 影响

历史值不再被日常重算破坏；代价是多两次窗口读（每条腿各一次 SELECT，窗口仅 10 天），
以及"某天确实该变成 NULL"的修订会被拒绝并告警 —— 需要人工确认。

## 备选方案与否决原因

- **在共享 `upsert_metrics` 上加 `coalesce(excluded.value, 既有)`** —— 会改掉**所有**写入方
  （行业指标、手工回补、其它 scope）的语义，且"源侧缺数 ⇒ 落 NULL + 原因码"正是本仓库刻意的
  数据纪律（缺数不许落 0、不许前向填充）。要挡的不是"记下缺数"，而是"重算把历史改坏"。
- **缩短重算窗口到 1 天** —— 违背对账范式（"窗口内一律重拉"才自愈得了历史上的洞），
  且会把"某天写失败"变成永久缺口。
- **写前预检（先算再决定写不写）** —— 腿的服务内部各自 commit，外部无法拦截其写事务。
